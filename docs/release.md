# Сборка под раздачу (`tools/pack`, CI)

Каноничное описание того, как из репозитория получается то, что игрок
скачивает: [tools/pack](../tools/pack) — отбор ресурсов,
[.github/workflows/release.yml](../.github/workflows/release.yml) — сборка и
выкладка.

---

## 1. Что скачивает игрок

Архив на платформу: игра, папка `assets` рядом с ней и короткий `README.txt`.

```
pixel-arpg-windows-amd64/
  pixel-arpg.exe
  assets/…
  README.txt
```

Ресурсы **не вшиты в бинарник** — по той же причине, по которой они не вшиты в
сборку из исходников: пока контент правится каждый день, важнее менять PNG без
пересборки. Плата за это — игру нельзя переносить одним файлом, и об этом
сказано в `README.txt` архива.

Игра ищет `assets` сначала в рабочем каталоге, потом **рядом с собой**
(`findAssets` в [cmd/game/main.go](../cmd/game/main.go)). Второе — не удобство,
а необходимость: запущенная двойным кликом программа получает рабочим каталогом
что угодно, и относительный путь до ресурсов не существует.

---

## 2. Правило отбора: едет то, что может появиться

Полные `assets/` — около 60 МБ, из них в забеге показывается меньше трети.
Остальное — семнадцать биомов, куда игра пока не ходит, демоны и личи из
подземелий, дома деревни, к которым нет кода. Игрок скачивал бы это зря.

`tools/pack` спрашивает не человека, а данные:

| что | правило |
|---|---|
| биомы | только те, в которые игра ходит — `scene.GameBiome`; из биома не едет `authoring/` (материал разметки, нужен tools, не игре) |
| звери | у кого `habitat.biomes` пересекается с биомами сборки |
| враги и боссы | то же правило по их `habitat.biomes` |
| детёныши и спутники | едут за взрослым: `young_form`, `grows_into`, `spawn.with` — они появятся вместе с ним |
| локации | не едут вовсе: ассеты есть, кода под них нет |
| герой, вещи, интерфейс, звук | едут целиком — показываются всегда |
| музыка | тема биома, которого нет в сборке, не едет; оставшаяся сжимается в OGG |
| паки существ | из пака едет только то, что назвал манифест: сетки диагоналей (`dir8/`), слои для перекраски (`parts/`) и прежние четырёхсторонние листы остаются дома |
| иконочные паки | лист, с которого не берут ни одной иконки, не едет — в паке рыбалки их десять, а нужен один |

Выходит около 7 МБ вместо 60. Крупных источников веса три, и «лишние мобы» из
них только один:

| | было | стало |
|---|---|---|
| паки существ и героя | 16 МБ | 4 МБ |
| музыка (WAV → OGG) | 5.5 МБ | ~1 МБ |
| чужие биомы и локации | 38 МБ | 1 МБ |

Больше всего съедали не сами кадры, а материал для их правки, лежащий в тех же
папках: у героя на 155 КБ рисуемых листов приходилось 1.8 МБ сеток и слоёв.

## 3. Таблицы переписываются, а не только папки

Выброшенное существо исчезает и из `species.json` / `enemies.json` /
`bosses.json`. Иначе бестиарий показывал бы карточки без спрайтов, а спавнер
знал бы про тварей, которых нет на диске.

По той же причине чистятся ссылки, которые после отбора повисли:

- `threat.prey` — лиса охотится на кроликов, но кроликов в лесной сборке нет;
- `spawn.json → limits.per_type_overrides` — поправка на демонов в сборке без
  демонов;
- `spawn.json → tiers.biome_shift` — сдвиг тиров для биомов, которых нет.

Это не косметика: ссылка в пустоту — то самое расхождение таблицы с миром,
которое ловит `Catalog.Validate()`, и лучше ему не доехать до игрока.

## 4. Проверка

После сборки `pack` открывает получившийся каталог **теми же загрузчиками, что
и игра** (`-check`, включена по умолчанию): манифест и атласы биома, таблицы
зверей, врагов, поведения, спавна, персонажа, вещей — плюс проверка, что у
каждого оставшегося пака на месте манифест и все кадры, которые он обещает.

Каталог, где ссылка ведёт в пустоту, — это сборка, которая упадёт у игрока.
Пусть падает здесь.

```bash
go run ./tools/pack -out dist/assets            # как в CI
go run ./tools/pack -out dist/assets -biomes forest,swamp
```

## 5. Кто и когда собирает

Каждый пуш в `main` (и запуск руками) поднимает
[Release](../.github/workflows/release.yml):

1. **ресурсы** — один прогон `tools/pack` на Linux; результат общий для всех
   платформ, потому что ресурсы платформы не знают;
2. **сборка** — три раннера: `linux-amd64`, `macos`, `windows-amd64`. На
   Windows cgo не нужен вовсе (`CGO_ENABLED=0`), зато нужен `-H=windowsgui` —
   иначе за игрой висит чёрное окно консоли. macOS собирается универсальной
   (обе архитектуры на одном раннере, `lipo` поверх): отдельный раннер под
   Intel выдают по получасу, а игрок не должен выбирать между «M1» и «Intel»,
   чтобы запустить игру;
3. **релиз** — архивы складываются в новый релиз `build-N`, помеченный `latest`.
   Ссылки в README ведут на `releases/latest/download/…` и поэтому не
   устаревают.

Сборки не подписаны: на macOS первый запуск — правым кликом и «Открыть».
